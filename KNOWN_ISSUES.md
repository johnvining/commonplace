# Known Issues

- **Audit other places where the pill input would fit.** The `PillInput`-style component (`AuthorsChipList` / `IdeasPillList` / `PilesPillList`) is now the pattern for multi-select autocomplete: chips + inline input + dropdown of suggestions + Backspace/× to remove. Used on authors (Note, Work), ideas (Note), piles (Note, Work). Other autocomplete usages haven't been audited — sweep `grep -nE "Autocomplete\b" site/` and review each remaining call site. Likely candidates: anywhere the user currently picks multiple of something via the legacy `Autocomplete` + chip-row pattern. Single-select autocomplete (Work field on a Note, search bar) does NOT need this — keep those as-is. Also: extract the three pill-list components into a shared `PillInput<T>` to remove the ~80% duplication.

- **Work rows on entity pages don't show piles or note count.** The `<ResultWork>` rows shown on Author pages (and anywhere else works are listed — Pile pages, search results, etc.) currently show only the work's name, year, and authors. Should also show: (1) the work's piles as chips (using the same `Prefix: Name` rendering as `PileLabel`), and (2) the note count (`note_count` is already returned by `findWorksByString` via the with-counts aggregate — wire that into the row). For Author specifically: extend the controller (`reqGetWorksForAuthor`) to populate piles and to either compute note_count via aggregate or join from notes. Same display change in `ResultWork.tsx` so it applies to every caller.

- **`cplace` CLI lacks "show contents of entity" commands.** Today's `cp piles <query>` / `cp authors <query>` / `cp ideas <query>` / `cp works <query>` only run the autocomplete — they list entities matching the query, not what's *inside* them. Need an additional command (e.g. `cp pile show <id-or-nick>`) that calls the existing server endpoints — `GET /api/pile/:id/notes`, `/api/pile/:id/works`, `/api/auth/:id/notes`, `/api/auth/:id/all-notes`, `/api/auth/:id/works`, `/api/idea/:id/notes`, `/api/work/:id/notes` — and prints the result. Same shape needed for every entity type that contains notes/works.

- **Works don't track a "posted / published" status.** "What have I read but not written about yet?" is a recurring question that requires manual cross-referencing across piles right now. A clean fix would be: (1) add a `posted: { type: Boolean, default: false, index: true }` field (or a `posted_at: Date`, which carries the same info plus a timestamp) to `server/src/resources/work/work.model.ts`; (2) include it in `WORK_WRITABLE`; (3) extend `findWorksByString` / autocomplete endpoints to accept an optional `posted?: boolean` filter so the URL `POST /work/autocomplete { string, posted: false }` works; (4) surface it in `cp works --unposted` (and `cp export --piles ... --unposted` to bulk-pull all reading piles minus already-posted works in one call). Migration: `db.works.updateMany({ posted: { $exists: false } }, { $set: { posted: false } })`. Workaround until then: maintain a `Status: Posted` pile and subtract its `works` from the reading piles client-side (`cp export --piles "Reading: *"` plus `cp show "Status: Posted"` and set-difference).

- **Pi MongoDB is on EOL 4.4.8.** Pinned in `docker-compose.yml`. MongoDB 4.4 EOL'd in Feb 2024; no upstream security patches. App works fine — not blocking — but worth upgrading in a maintenance window. **Use dump/restore (mongodump + mongorestore), not the in-place FCV version walk.** Concretely: with the old container running, `docker exec commonplace-mongo-1 mongodump --out=/data/db/dump-pre-upgrade`; `docker-compose down`; reset the `mongo-data` volume; bump image to `mongo:7.0` (LTS through July 2027) in docker-compose.yml; `docker-compose up -d`; `docker exec commonplace-mongo-1 mongorestore /data/db/dump-pre-upgrade`. Cost: brief downtime + doubled disk during transfer. **Critical rule:** never start a binary against data more than one major version older — doing so rewrites WiredTiger checkpoints into a format the older binaries can no longer read, locking you between FCV-too-old and WT-too-new. Dump/restore sidesteps this entirely because BSON is version-portable.
